# Философия RURQE

**RURQE** (**R**ust **U**niversal **R**elational **Q**uery **E**ngine) — это строго типизированный построитель SQL-запросов, движок реляционного исполнения и инструментарий кодогенерации «от базы данных» для Rust.

## Проблема, которую решает проект

Классический разрыв в доступе к реляционной базе из прикладного кода выглядит так:

1. **Схема живёт в двух местах.** DDL-миграции описывают одно, структуры приложения — другое, и расхождение обнаруживается в рантайме (`column "..." does not exist`), а не при сборке.
2. **SQL — это строка.** Строка не проверяется компилятором: опечатка в имени колонки, ссылка на таблицу, которой нет в `FROM`, чтение колонки `LEFT JOIN` как не-nullable значения — всё это ошибки исполнения.
3. **Типы теряются на границе.** `SELECT` возвращает кортеж без имён, `Option<T>` появляется и исчезает произвольно, а `NULL` из внешнего соединения приезжает в поле, объявленное как `T`.

RURQE формулирует ответ на это как один инвариант: **если запрос скомпилировался, он семантически корректен для целевого диалекта и версии движка**. Невалидный запрос не должен доходить до базы.

## Пять принципов

### 1. Код — единственный источник правды (Code as SSOT)

Схема извлекается из живого каталога базы (`pg_catalog`, `information_schema`, `PRAGMA`-таблицы SQLite), а не переписывается вручную. Из неё генерируются zero-sized маркеры таблиц и колонок, DTO-структуры и снимок каталога `schema.lock` с контрольной суммой `SCHEMA_HASH`.

Этот же принцип распространяется на саму книгу, которую вы читаете: любое утверждение о гарантии компилятора или о поведении рантайма подтверждается конкретным местом в кодовой базе или существующим тестом. Документация, описывающая возможность, которой в коде нет, считается дефектом, а не неточностью формулировки.

### 2. Zero Database Rejection

Ни один синтаксически или семантически невалидный запрос не должен достигать движка базы. Ошибка ловится либо компилятором (Tier 1), либо детерминированной проверкой при сборке запроса (Tier 2) — см. [Two-Tier SQL Correctness](two_tier.md).

### 3. Native-or-Nothing

Если возможность нельзя выразить нативно на целевом движке, она не эмулируется. `FOR UPDATE` на SQLite не превращается в «примерно то же самое» — метода просто нет в наборе возможностей диалекта (`SupportsRowLocking` не реализован для `Sqlite`), и код не компилируется. Ту же политику разделяет `MERGE`: синтетическая эмуляция через `SELECT` + `INSERT/UPDATE` создаёт гонки и запрещена.

### 4. Zero-Cost

Диалект — это zero-sized фантомный параметр типа (`SelectQuery<Postgres<Pg16>, ...>`), маркеры таблиц и колонок — это ZST, рендеринг запроса — один проход по записанному AST в `String` с вектором параметров. Ни виртуальных вызовов, ни рефлексии, ни GC.

### 5. KISS, YAGNI, DRY

Никаких «полей на всякий случай». Мёртвый код удаляется сразу. Для стандартных форматов (TOML, JSON) и криптографии используются зрелые крейты, а не самописные парсеры; исключения фиксируются явно и обоснованно.

## Что даёт это на практике

| Обещание | Механизм в коде |
|---|---|
| Опечатка в колонке — ошибка компиляции | `Column`, `TableInScope`, `ExprInScope` |
| `NULL` из `LEFT JOIN` нельзя прочитать как `T` | `TableNullabilityInScope`, `MakeNullable`, `ApplyNullability` |
| `UPDATE` без `WHERE` не выполнится случайно | тип-состояние `ExecutableMutation`, `.allow_all()` |
| Неподдерживаемая движком конструкция не компилируется | capability-трейты (`SupportsReturning`, `SupportsRowLocking`, …) |
| Неоднозначный `JOIN` отклоняется до отправки в базу | `BuildError::DuplicateRelation` в `.build()` |
| Схема не расходится с кодом | `cargo db-codegen`, `schema.lock`, `cargo db-verify` |
