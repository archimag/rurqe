# From Codd's relational algebra to the Rust type system

This chapter maps every relational algebra operator onto a concrete location in the code base: a type, a trait, a method, and an SQL clause. Nothing is approximate — only what is implemented and covered by tests.

## The data level

### Relation

| Algebra | RURQE |
|---|---|
| Relation name and schema | `Table` with the `NAME` constant, usually generated by the `table!` macro |
| Header (the set of attributes) | A set of ZST types implementing `Column` |
| A relation instance inside a query | `TableScope`, an ordered list of relations |
| A relation reference carrying an alias | `TableRef { name, alias }`, `Table::table_ref()` |

`TableScope` can produce both names (`push_table_names`) and full references for rendering (`push_table_refs`). The default implementation derives the second from the first, while `Aliased<T, A>` overrides the method so that `AS "alias"` reaches the `FROM` clause.

### Attribute

```rust
pub trait Column {
    type Table: Table;
    type RustType;
    const NAME: &'static str;
    fn expr_kind() -> ExprKind;
}
```

`Column::RustType` is the bridge between the SQL type and the Rust value type: `VALUES`, `SET`, comparisons, and row decoding are all checked against it. `ColumnBelongsTo<T>` statically asserts that the column belongs to the table.

## Unary operators

### Selection σ (filtering)

- Algebra: the subset of tuples satisfying a predicate.
- RURQE: `.where_(Expr<bool, Scope>)`, plus the dynamic forms `.where_opt`, `.where_if`, `.when`, `.if_some`.
- SQL: `WHERE`.
- Invariant: the predicate must be an `Expr<bool>` and may reference only relations of the scope (`ExprInScope`).

### Projection π

```rust
pub trait SelectTarget { type RustType; fn to_expr_kind(&self) -> ExprKind; }
pub trait Selection { type Row; fn push_projections(&self, out: &mut Vec<ExprKind>); }
```

- Algebra: selecting a subset of attributes while preserving their order.
- RURQE: `.select((UserId, UserName))` for a tuple, `cols!` for a list, `select!` / `dto!` for named fields.
- SQL: the projection list.
- Invariant: `SelectionFor<Tables, Positions, D>::Row` computes the row type taking the nullability of the scope into account; projecting a column outside the scope is rejected by `SelectTargetInScope`.

`Selection::push_projections` has no default body: an implementation must enumerate the projected nodes, otherwise the query would render `SELECT  FROM ...`. An empty list is rejected as well by the pre-flight check (`BuildError::EmptyProjection`).

### Ordering and pagination

- RURQE: the `.order_by_*` family (including `_nulls_first` / `_nulls_last` through `SupportsNullsOrdering`), `.limit`, `.offset`.
- SQL: `ORDER BY`, `LIMIT`, `OFFSET`.
- Invariant: ordering by a column requires that column to be in scope; under `DISTINCT` and `DISTINCT ON` the alignment with the projection is Tier 2 (see `BuildError::DistinctOrderNotProjected` and `BuildError::DistinctOnOrderMismatch`).

## Binary operators

### Theta join ⋈θ

```rust
select_from(Users).inner_join_table(Orders, Expr::column::<OrderUserId>().eq(Expr::column::<UserId>()))
```

- Result type: `SelectQuery<D, Joined<Tables, T>, ...>`.
- SQL: `INNER JOIN ... ON`.
- Invariant: the predicate is checked against the already extended scope `Joined<Tables, T>`, so a column of the new table is admissible while an unrelated one is not.

### Left outer join ⟕

- Type: `SelectQuery<D, LeftJoined<Tables, T>, ...>`.
- SQL: `LEFT JOIN ... ON`.
- Invariant: `TableNullabilityInScope<T, At<0>> for LeftJoined<..>` returns `NullableRel`, so projecting the column yields `Option<T>` (see [Nullability](nullability.md)).

### Full outer join ⟗

- Type: `FullOuterJoined<Tables, T>`; requires `D: SupportsFullOuterJoin`.
- SQL: `FULL OUTER JOIN ... ON`.
- Invariant: **both** sides lift — the `TableNullabilityInScope` implementation for `FullOuterJoined` returns `NullableRel` for the new table and for every table of the inner scope.

### Cartesian product ×

- `cross_join_table(T)` → `CrossJoined<Tables, T>`; `Nullability = NonNullableRel`.
- SQL: `CROSS JOIN`.

### Correlated join (LATERAL)

- `cross_join_lateral(Lateral<T, ..>)` → `CrossLateralJoined` (NonNullable), `left_join_lateral(...)` → `LeftLateralJoined` (Nullable).
- Requires `D: SupportsLateralJoin` (PostgreSQL only).
- SQL: `JOIN LATERAL (SELECT ...) AS "t"`, and for the left form `LEFT JOIN LATERAL ... ON true`.

## Grouping and aggregation

### γ (grouping)

- `.group_by((UsersId, UsersName))` moves the query into `GroupedQuery<D, Tables, Output, GroupByCols, Projected>`.
- SQL: `GROUP BY`.
- Invariant: only grouped columns, aggregates, literals, and window expressions implement `GroupedSelectTarget`; an attempt to project an ungrouped column is a compile error, including when the column is hidden inside `coalesce` / `CASE` (tracked by `FunctionOperand` and `CombineAggr`).
- Residual cases (for example `HAVING` over an ungrouped column) are covered by Tier 2: `UngroupedHavingColumn`, `UngroupedColumn`, `UngroupedColumnWithAggregate`.

## Set operations

| Algebra | Method | Typestate |
|---|---|---|
| ∪ | `.union(other)`, `.union_all(other)` | `Compound`, then `TailClosed` after the first ordering |
| ∩ | `.intersect(other)` | the same |
| − | `.except(other)` | the same |

- SQL: `UNION` / `UNION ALL` / `INTERSECT` / `EXCEPT`.
- Tier 1 invariant: the operands must share the same dialect and the same row type, and `SetOperand` is unavailable after `TailClosed`, so no operand can follow the ordering of the combined rows.
- Tier 2 invariant: `SetOperandArity`, `CompoundOrderIndex`, `CompoundOrderColumn`, `CompoundOrderExpression`.
- Ordering the combined rows is possible only through output names or 1-based positions: `.order_by_output_*`, `.order_by_index*`.

## Semijoins and antijoins

| Algebra | RURQE | SQL |
|---|---|---|
| Semijoin ⋉ | `exists(subquery)` | `EXISTS (SELECT ...)` |
| Antijoin ▷ | `not_exists(subquery)` | `NOT EXISTS (SELECT ...)` |
| Semijoin on an attribute | `col.in_subquery(sub)` | `IN (SELECT ...)` |
| Antijoin on an attribute | `col.not_in_subquery(sub)` | `NOT IN (SELECT ...)` |
| Tuple semijoin | `(a, b).in_subquery(sub)` through `RowExpr` | `(a, b) IN (SELECT ...)` |

Invariant: `InSubquery<Row>` ties the expected row type to the projection of the nested statement — the scalar form accepts only `(T,)`, the tuple form accepts exactly the declared arity and types. A mismatch is rejected by `rustc`.

Relational division has no dedicated method: it is expressed by composing `not_exists` / `exists`.

## Nested relations (NF²)

- `nest_many(query)` → `Vec<Row>`, `nest_one(query)` → `Option<Row>`.
- Requires `Row: MultisetRow` with the `FIELDS` constant and `QueryD: SupportsJsonAggregation`.
- SQL: PostgreSQL — `jsonb_agg(to_jsonb(...))` with `COALESCE(..., '[]'::jsonb)`; a dialect without native row aggregation builds `json_object` objects and a `json_group_array` array.
- Details: [NF² and MULTISET](nf2_multiset.md).

## Summary of invariants

| Operator | What the compiler checks | What `.build()` adds |
|---|---|---|
| σ, π | scope, predicate type, row type | empty projection |
| ⋈θ, ⟕, ⟗, ×, LATERAL | scope, nullability, capability | duplicate relations |
| γ | grouping or aggregate | `HAVING` and residual references |
| ∪ / ∩ / − | same dialect and row type, clause order | operand arity, ordering form |
| ⋉ / ▷ | subquery arity and types | — |
| NF² | `MultisetRow`, JSON aggregation capability | — |
