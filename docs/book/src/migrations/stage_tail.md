# Stage + Tail: декларативный stage и cold start

Вторая модель добавляет к раннеру источник истины о том, какой схема должна быть. Живая база по-прежнему продвигается скриптами, но чистая база создаётся из декларации.

## Каталоги

```text
project/
├── schema/                     # декларативный stage (SSOT структуры)
│   ├── users.sql
│   └── billing.sql
├── migrations/                 # активный хвост
│   ├── checkpoint.toml         # граница прунинга
│   ├── checkpoint-stage/       # снимок stage на границе (verbatim)
│   ├── checkpoint.lock         # секция сериализации писателей
│   └── V051__add_credits.sql
├── schema.lock                 # детерминированный снимок каталога
└── rurqe.toml
```

## `DeclarativeStage`

Stage — это просто каталог с `*.sql`:

- `DeclarativeStage::DIRECTORY == "schema"` — имя по умолчанию (переопределяется `--stage-dir`);
- `DeclarativeStage::load(dir)` возвращает `Ok(None)`, если каталога нет, и ошибку, если файл не читается (молчаливый пропуск скрипта инициализировал бы базу неполной схемой);
- скрипты сортируются по имени, чтобы порядок применения не зависел от порядка обхода файловой системы;
- транзакционность определяется тем же парсером атрибутов, что и у миграций (`StageScript::new` → `parse_script_attributes`);
- `DeclarativeStage::checksum()` — SHA-256 конкатенации `имя + \n + sql + \n` в порядке применения: перестановка файлов не меняет дайджест, правка любого скрипта — меняет.

## Cold start

`cold_start(backend, stage, marker)` создаёт базу с нуля:

1. Берёт run-лок и гарантирует таблицу истории.
2. Читает историю и ищет последнюю запись `<< Stage >>`:
   - если дайджест каталога, который реально видит backend (`guard.catalog_checksum()`), совпадает с записанным и версия совпадает → команда сообщает «уже инициализирована», ничего не делая;
   - если дайджест разошёлся → `Error::InvalidStage` с указанием переинициализировать базу или сначала закоммитить текущий stage;
   - если найдена провалившаяся (in-progress) запись `<< Stage >>` → `Error::InvalidStage` о прерванном cold start;
   - если история непуста чем-то другим → `Error::BaselineAlreadyExists`.
3. Если в stage есть нетранзакционные скрипты, заранее коммитит in-progress маркер (`success = false`), чтобы падение посреди прогона было диагностируемо.
4. Применяет stage: подряд идущие транзакционные скрипты — в одной транзакции, каждый нетранзакционный — отдельно.
5. Считает итоговый дайджест каталога, записывает применяемый маркер (`success = true`) и, если был in-progress маркер, удаляет его в той же транзакции.

Возвращаемый `ColdStartReport` содержит `stage_scripts` (имена применённых файлов), `installed_rank` и `total_time_ms`.

### Что именно попадает в историю

`StageMarker` пишется как обычная строка истории:

| Поле | Значение |
|---|---|
| `version` | версия, переданная в `--version` |
| `description` | `--description` (по умолчанию `stage`) |
| `kind` | `MigrationKind::Baseline` |
| `script` | `STAGE_SCRIPT == "<< Stage >> "` (константа `<< Stage >>`) |
| `checksum` | дайджест каталога, а не дайджест текста DDL |
| `execution_time` | 0 |

Версия этого маркера — и есть граница: всё, что ниже или равно, раннер считает пройденным.

Важная деталь: маркер анкорит *канонический* дайджест каталога (`SchemaCatalog::checksum()`), который backend выводит интроспекцией того, что реально создано. Поэтому маркер совпадает с `checkpoint.toml`, созданным через `stage commit`, независимо от движка. Backend, который не умеет интроспектировать себя, остаётся при переданном дайджесте stage.

## Команды

```bash
cargo rurqe stage init --version <version> [--stage-dir <dir>] [--description <desc>] \
                       [--database-url <url>] [--schema <name>]
```

Пустой stage отвергается («holds no `*.sql` script to apply»), а на уже инициализированной базе команда сообщает «Database already initialised at stage X; nothing to apply».

```bash
cargo rurqe stage commit --version <version> [--stage-dir <dir>] [--lock-path <path>] \
                         [--checkpoint-path <path>] [--database-url <url>] [--schema <name>]
```

`stage commit` — это шов между двумя моделями. Он:

1. загружает stage и интроспектирует живой каталог;
2. прогоняет гейт паритета: `compare_stage_with_live` материализует stage в scratch-базе и сравнивает каталоги. Расхождение → ошибка с перечислением находок и напоминанием, что гейт сработал *до* секции чекпоинта, то есть ни один артефакт не тронут;
3. рендерит `schema.lock` (`catalog.to_lock()`) и `Checkpoint::new(version, catalog.checksum())`;
4. собирает снимок границы (`<stem>-stage/`) во временном каталоге рядом с целевым и синхронизирует его;
5. входит в секцию `checkpoint.lock`, выметает мусор прошлых попыток, восстанавливает прерванный коммит, проверяет запрет отката (нельзя понизить версию чекпоинта), пишет `schema.lock` и выполняет `seal_commit`;
6. отдаёт отчёт: починка (если была), предупреждение о «пустой» выборке схемы (если было), замечания swap.

Детали шагов 5 и 6 — в разделе [Протокол чекпоинтов](checkpoint_protocol.md).

## Scratch-базы

Материализация stage выполняется в отдельной базе, чтобы декларативный DDL никогда не выполнялся над живым каталогом:

- PostgreSQL: используется тот же URL (материализация создаёт одноразовую scratch-базу);
- SQLite: `:memory:` — URL указывает на тот самый файл, который коммит запечатывает.

Осиротевшие PostgreSQL scratch-базы убирает `stage cleanup` — только базы, помеченные этим хостом, старше `--older-than` и не принадлежащие живому процессу; без `--yes` команда лишь перечисляет кандидатов.
